## 一、戏剧法:一个舞台,两个演员

CPU 是舞台,寄存器组是演员的"临场状态"。两个任务轮番上台,关键在
**换场速度**:每次换场要把上台演员的状态完整存档、把下台演员的
存档完整恢复,快到观众(你)看不出停顿。

这个"存档"在内核里叫**上下文(context)**,布局 136 字节
(`kern.c` 的 `struct ctx`,与 `kern.S` 的偏移一一对应):

```
偏移     内容
0~120    x1~x31(31 个通用寄存器,x0 恒零不用存)
124      mepc(被打断处的地址)
128      mcause(打断的原因)
132      mstatus(中断开关状态)
```

## 二、硬件部分:trap 时 CPU 自动做什么

`rv/cpu.py` 的 `_trap_now()`——定时器到点、U 模式 ecall、非法指令,
最终都走这里。硬件(我们的模拟器)自动做四件事:

```python
self.csr[0x341] = self.pc            # mepc ← 被打断的地址(记得回来)
self.csr[0x342] = cause              # mcause ← 打断原因
ms = ...                             # mstatus:MIE→MPIE,MIE←0
self.csr[0x300] = (ms & ~0x88) | ((ms & 0x8) << 4)
self.mode = 3                        # 升入 M 模式(内核)
self.pc = target                     # PC ← mtvec(内核入口)
```

第二条最重要:**进内核后中断自动关闭**。现场存到一半再被打断,
就是灾难片。`mret` 反向操作:`MIE←MPIE`(重新开中断)、
`mode←MPP`(回用户态)——**M 和 U 两级特权,靠 mstatus 里的这两个位
完成切换**。

## 三、内核部分:kern.S 逐段精读

### 3.1 mscratch 交换:一条指令找到自己的存档位

```asm
trap_entry:
    csrrw sp, 0x340, sp     # sp ↔ mscratch 一次性互换!
```

`mscratch`(0x340)永远持有"当前运行任务"的 ctx 指针。这条指令之后:
sp 指向自己的 ctx(可以存现场了),任务原来的 sp 被暂存在 mscratch。
**一条指令,完成"从任务视角切换到内核视角"。**

### 3.2 31 连存:一个都不能少

```asm
    sw x1, 0(sp)
    sw x2, 4(sp)
    ...                     # x1~x31 全部入档
    sw x31, 120(sp)
    csrrs t0, 0x340, x0     # 真实任务 sp 被换到了 mscratch
    sw t0, 4(sp)            # 补写 x2 槽位!
```

为什么一个寄存器都不能省?因为**被切换走的任务还会回来**——它对
"世界"的全部记忆就是这 31 个值。少存一个,回来时那个变量的值就
是别人的了。

### 3.3 restore_ctx:像从过去恢复

```asm
restore_ctx:
    csrw 0x340, a0          # mscratch ← 新任务的 ctx
    addi sp, a0, 0
    ...                     # mepc/mstatus 写回 CSR,31 个寄存器逐个装回
    lw x2, 4(sp)            # sp 必须最后恢复!
    mret                    # MIE←MPIE,mode←MPP,pc←mepc
```

`mret` 是整个机制的句号:它同时完成"回到被打断处"和"降回用户态、
重开中断"。

## 四、教学案例:那个让任务栈形同虚设的 bug

这是本项目最值得复盘的事故,完整重现"现象→定位→根因"三层法。

**现象**:内核 v1 里任务 A 打 'A'、B 打 'B',一切正常。直到任务改用
C 的栈(putdec 的 buf 数组),输出变成乱码,数据诡异损坏。

**定位(三层递进)**:

1. 输出模式断言:`[0][1][2]` 连读 → 有任务没被调度;`wasd` 不回显 → 链路断点
2. 存储监视点:子类化 CPU 拦截 `write()`,对 ctx+4(sp 槽位)记录
   每次写入的 PC → 抓到 `pc=0x240` 反复写入"ctx 指针"这个怪值
3. 反汇编:用 CPU 自己的 `decode()` 翻译 0x240 → 它就是 `trap_entry`
   的第一条 `csrrw sp, 0x340, sp`!

**根因**:交换指令执行后,x2(sp)**已经是 ctx 指针**了。接下来的
保存循环老老实实把 x2 存进 ctx+4——存进去的是 ctx 指针,不是任务
的栈指针!任务的真 sp 此刻只活在 mscratch 里,却没人管它。

**修复**(就两条指令):

```asm
    csrrs t0, 0x340, x0     # 从 mscratch 读回真实任务 sp
    sw t0, 4(sp)            # 补写 x2 槽位
```

**教训**:交换类技巧必须回答一个问题——**"我的数据现在到底在
哪一份里?"** 修好之前,任务从未真正用过自己的栈(它们恰好只碰
寄存器),所以冒烟测试一度全绿。**测试全绿 ≠ 没有潜伏 bug,
只说明潜伏 bug 还没被踩到。**

## 五、init_ctx:伪造一个"从未运行过"的过去

新任务没跑过,哪来的"被打断现场"?`init_ctx()` 直接**编造**一份:
mepc = 任务入口、sp = 栈顶、mstatus = MPIE(1)、其余全 0。
`mret` 一执行,就像这个任务"从很久以前的中断里恢复"一样开始运行。
操作系统创建新进程用的正是这个把戏。

## 本章小结

- 上下文 = 136 字节的"演员存档";切换 = 存 A、取 B、mret
- 硬件做四件事(mepc/mcause/关中断/进内核),内核做其余
- mscratch 交换一条指令换视角;真实 sp 要从 mscratch 补写回
- init_ctx 伪造过去,mret 就是时光机
- 测试全绿只说明"踩到的都没问题"——覆盖度永远值得追问
