# 06 · MMIO:外设即寄存器

> 这一章你会学到:CPU 只会读写内存,那"外设"是怎么存在的——答案是
> 把某些地址接上设备,这叫内存映射 I/O(MMIO)。读完这章,framebuffer、
> UART、键盘、定时器四件套在你眼里都只是"会耍脾气的内存"。
> 配套源码:`riscv/rv/cpu.py` 的 `read()/write()` + `c/bounce.c`

## 先跑起来

```bash
cd ~/computer-lab/riscv
bash c/build.sh bounce
python3 -m rv.emu c/bounce.bin --fb-every 60000 | head -20
```

每隔几万条指令,你看到一张 ASCII 小地图里有一颗球在动。
球不是 CPU 画上去的"魔法"——它就是 C 程序往**几个特殊地址**
写了一些字节而已。

## 一、核心思想:外设即寄存器

CPU 硬件上只会做一件事:按地址读写内存。那屏幕、键盘怎么接?
答案朴素得惊人——**给每个设备划一段地址,读写这些地址时,
信号不进内存条,而是通向设备**:

```
        CPU 发出地址
            │
            ▼
 ┌──────────────────────┐
 │ read()/write() 路由器 │        ← rv/cpu.py 里就是这个 if/elif
 ├──────────────────────┤
 │ 0x80000000~  RAM     │ → 真内存(bytearray)
 │ 0x10000000   UART    │ → 串口(写=打字,读=查键盘)
 │ 0x10001000   FB      │ → framebuffer(256 字节位图)
 │ 0x02004000   CLINT   │ → 定时器比较寄存器
 │ 其余          未映射   │ → 读 0,写忽略
 └──────────────────────┘
```

`read()`/`write()` 就是这台机器的"地址译码器+总线"。真实计算机的
主板总线干的是同一件事,只是硬件化而已。**对外设的一切操作,
本质都是普通的 load/store**——这就是"内存映射 I/O"。

## 二、UART:一个字节的独角戏

```
0x10000000 + 0   写一个字节 → 串口发出(收集在 uart_out)
0x10000000 + 4   读 → 1=有键盘输入,0=无
0x10000000 + 8   读 → 弹出一个输入字符,空则 0xFFFFFFFF
```

`hello.c` 里 `*UART = (unsigned char)c;` 就是一条 `sb` 指令——
写内存,但"内存"的另一头连着终端。你在屏幕上看到的每一个字符,
都是 CPU 往同一个地址写了 17 次。

输入设备是经典的**双寄存器设计**:状态寄存器(有货吗?)+
数据寄存器(取走一个)。`poll_keys()` 的
`while (*IN_READY) { k = *IN_DATA; ... }` 就是教科书式的排空循环。

## 三、framebuffer:256 字节的显示器

```
0x10001000 起,64×32 位图
每行 8 字节(64 像素 ÷ 8),共 32 行 × 8 = 256 字节
MSB = 行内最左像素
```

`bounce.c` 的 `draw_sprite()` 现场解剖——画一颗 8×6 的球:

```c
volatile unsigned char *p = FB + (y + r) * 8 + x / 8;   // 定位字节
*p ^= (unsigned char)(sprite[r] >> shift);              // 异或 8 位
if (shift) p[1] ^= sprite[r] << (8 - shift);            // 跨字节平移
```

三个知识点:① `x/8` 和 `x%8` 是"第几个字节、字节内第几位";
② XOR 画/擦一体(CHIP-8 章的老朋友);③ 球在字节边界上时,
一行要**横跨两个字节**写——`>> shift` 和 `<< (8-shift)` 各管一半。

**`volatile` 为什么必须加**:告诉编译器"这个内存你不知道会怎么变,
每次都必须真的读写"。没有它,优化器可能把延迟循环整个删掉。

## 四、CLINT:给死循环的机器装上闹钟

```
0x0200BFF8   mtime    64 位计数器(我们的设计:每执行 1 条指令 +1)
0x02004000   mtimecmp 64 位比较值:mtime ≥ mtimecmp → 定时中断待触发
```

这是整个操作系统的地基:内核把 mtimecmp 拨到"未来某刻",
CPU 跑到那儿就会触发 trap,调度器接管——**时间片就是这么来的**。
两个设计决定值得注意:

1. **每条指令 +1**:不模拟真实晶振频率,换取完全可重现的测试
   (同程序同输入 → 同时刻同中断)
2. **复位值 0**:mtimecmp 复位为 0 意味着 MTIP 立即挂起——所以软件
   必须在开中断前先写 mtimecmp(我们踩过的真实坑,见 README)

64 位寄存器怎么被 32 位 CPU 读?拆两个 32 位窗口:`0x0200BFF8`
读低半、`0x0200BFFC` 读高半——真实 CLINT 就是这么设计的。

## 五、未映射的地址:宽容还是报错?

本机对未映射地址**读返回 0、写直接忽略**。真实硬件的总线也是类似
行为(读回来全 1 或 0 的"垃圾")。为什么不一发现越界就报错?
因为在真实硬件上"地址上什么都没接"是常态;把校验留给软件
(本项目的越界报错只保护 RAM 内部)。

## 本章小结

- 外设即寄存器:划分地址段 + 路由器,一块屏幕就是 256 字节
- 设备三件套:写=输出(UART/FB),读=输入(键盘双寄存器),
  对比寄存器=时钟(CLINT)
- volatile 不是装饰,是对优化器的声明
- "每条指令 +1"的虚拟时钟:用真实性换可重现性,测试友好
