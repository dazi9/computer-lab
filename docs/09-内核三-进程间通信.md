`|+++<0><1><2>+++<3>` ——生产者发出的 tick,被消费者**按原样、按顺序**

邮箱。两个任务各干各的 = 两座孤岛;IPC(进程间通信)是修桥的工程。

## 一、信箱的接口:只有两个动词

```c
sys_send(v);        /* 投递:邮箱满了就睡,直到有空位 */
unsigned v = sys_recv();   /* 收取:邮箱空了就睡,直到有信来 */
```

注意它们的**阻塞语义**:不是"失败返回",而是**睡着等条件成立**。
这正是第 08 章睡眠队列的用武之地——IPC 和定时器共用同一套
SLEEPING 机制,只是唤醒方式不同。

## 二、环形缓冲:三件套撑起的队列

```
        head(读位置)          tail(写位置)
         ▼                     ▼
buf:  [ 3 ][ 4 ][ 5 ][ 6 ][  ][  ]
count = 4,CAP = 8
空:count == 0        满:count == CAP
```

```c
/* send(内核态) */
mail_buf[mail_tail] = v;
mail_tail = (mail_tail + 1) % MAIL_CAP;
mail_count++;
/* recv(内核态) */
v = mail_buf[mail_head];
mail_head = (mail_head + 1) % MAIL_CAP;
mail_count--;
```

head 追着 tail 跑,`% MAIL_CAP` 让数组首尾相接成环。**单生产者单
消费者的经典解法**,从 Unix 管道到网卡驱动,五十年没变过。

## 三、阻塞与唤醒:NEVER 哨兵的设计

任务等信时会睡去,但**不能被闹钟叫醒**——信没来就是没来。于是
`wake_at` 里放了一个特殊值:

```c
wake_at[id] = NEVER;         /* 0xFFFFFFFFFFFFFFFF:不是时间,是誓言 */
```

第 08 章的 `wake_due_tasks()` 只在 `t >= wake_at[i]` 时唤醒——
NEVER 永远不满足,**等信的任务只能被"投递动作"唤醒**:

```c
if (state[peer] == SLEEPING && wake_at[peer] == NEVER)
    state[peer] = RUN;       /* 只摇醒等信的,别吵睡定时器的 */
```

这个 `wake_at[peer] == NEVER` 检查是 v4 修出来的:初版唤醒不看原因,
把正在 `kern_sleep` 睡定时器的任务也摇醒了——定时被打断,节奏全乱。
**一个哨兵值,区分了两种"睡觉"的语义。**

## 四、为什么这里不需要关中断(而 sleep 需要)

细心的你会问:第 08 章 kern_sleep 有"关中断三步舞",send/recv 却
没有——它们不怕竞态吗?不怕,因为它们**住在内核里**:

send/recv 是系统调用,整个处理过程处于 trap 处理器中——
**中断早已被硬件关闭**(mstatus.MIE=0)。所有邮箱操作天然串行,
不需要任何额外锁。这也是设计规律:**能在特权级内原子完成的操作,
就不要发明锁**。多消费者场景才会真正需要锁(见练习 ★★★)。

## 五、最强断言:严格递增

```python
msgs = [int(m) for m in re.findall(r'<(\d+)>', out)]
assert msgs == list(range(len(msgs)))
```

一行断言,四重验证:**不丢**(每个 tick 都在)、**不重**(无重复)、
**不乱序**(FIFO 生效)、**速率匹配**(生产多少消费多少)。在 2M 条
指令的随机调度下,它像一张网,兜住任何调度器或邮箱的回归。

写行为断言的进阶技巧就在这:不要断言"输出长什么样",要断言
"**系统必须满足的性质**"——性质比形状稳健得多。

## 本章小结

- IPC 三要素:信箱(数据)、阻塞(等信)、唤醒(递信)
- 环形缓冲:head/tail/count 三件套,%CAP 成环,五十年不过时
- NEVER 哨兵:让"睡定时器"和"等信箱"的唤醒语义分离
- 内核态操作天然原子(MIE=0),锁只在真正需要的地方出现
- 性质断言 > 形状断言
